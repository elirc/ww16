# Debugging

The runtime fixture records `find`, `tx`, `update`, `approval`, `audit`, and `job`. It asserts every repository call inside the transaction receives the same `tx` object. Failure cases inject an adapter error and inspect the call prefix. When a test fails, first ask whether the pre-read happened outside the transaction, then whether the role was passed as `session.role`. Do not infer rollback from a rejected callback; the harness has no database.

Run `node --experimental-vm-modules --test tests/deal-transition-lab.test.mjs` from the project directory. If a permission case unexpectedly enters the transaction, inspect the real domain edge and role map rather than adding a fake permissions array to the session. If history lacks the note, inspect the service fallback from note to rejectionReason. If a job is unexpectedly scheduled after an audit error, compare the awaited sequence. The injected error object must propagate unchanged, so an identity assertion catches accidental wrapping or swallowing. A separate database test would force audit insertion to fail and then query persisted status and history using another connection. Only that provider test can substantiate rollback. Do not alter the adapter to simulate rollback and present the result as database proof.
