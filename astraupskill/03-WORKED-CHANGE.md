# Worked path

For a SUBMITTED deal and a permitted sales role, the service finds the deal, checks `SUBMITTED -> SALES_APPROVED`, opens a transaction, updates status, creates approval history with from/to values, and records audit. For an APPROVED transition, the same sequence includes a leaderboard job. A missing deal fails before policy. An invalid edge fails before transaction. If update fails, approval and audit are not reached; if audit fails, the transaction callback rejects. The source already implements this ordering; the course makes it executable.

For a concrete trace, use deal d1, actor u1, note reviewed, and next status SALES_APPROVED. The update payload identifies d1 and the new status. History includes fromStatus SUBMITTED, toStatus SALES_APPROVED, actorUserId u1 and the note. The audit action is deal.transitioned. The returned value is the updated repository record. For SALES_APPROVED to APPROVED under CHANNEL_MANAGER, the job adds type LEADERBOARD_REFRESH, status QUEUED, sourceEntity DealRegistration and sourceEntityId d1. Its quarter follows the real year-Q-number formatter. These assertions check meaningful data, rather than merely counting calls. Compare them with [the executable fixture](../tests/deal-transition-lab.test.mjs). The unchanged production source is retained as a reference snapshot for later experiments.
